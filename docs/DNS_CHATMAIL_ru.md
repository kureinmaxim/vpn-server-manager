# DNS / AdGuard Home и Chatmail — 4.12.12

В **Projects**, **Статус → Мои проекты** и **Monitoring → Мои проекты** автоматически
показываются две дополнительные роли, независимо от редактируемого списка проектов:

- **AdGuard Home / DNS**: службы AdGuardHome/adguardhome/adguard-home либо контейнер
  с образом AdGuard Home. Имя контейнера может быть произвольным. Доступны тег образа
  (не гарантия версии запущенного бинарного файла), Compose service и опубликованные
  Docker-привязки портов, когда Docker предоставляет эти данные.
- **Chatmail relay**: Postfix и Dovecot плюс не менее двух специальных служб
  doveauth, chatmail-metadata, filtermail, filtermail-incoming, filtermail-transport.
  Один Unbound, Postfix или обычный почтовый сервер не определяются как Chatmail.
  Nginx, Unbound, TURN, iroh, lastlogin, OpenDKIM и acmetool отмечаются как дополнительные;
  отсутствие этих служб не меняет состояние основных компонентов.

Обнаружение и состояние процессов **не подтверждают функциональную исправность**.
Ошибки SSH, Python 3, Docker/systemd и прав доступа дают «нет данных», а не «не установлен».
Не требуются Tailscale, Telegram-бот или установка скриптов мониторинга.

## Запуск проверки

Откройте **Monitoring → DNS / Chatmail** или ссылку на обнаруженный проект в статусе
сервера. Выберите роль, проверьте параметры и нажмите **Запустить проверку**.
Это разовая проверка с выбранного VPS через существующее SSH-подключение.
Кнопка **Сохранить параметры** записывает только параметры диагностики в уже используемый
зашифрованный файл серверов, сохраняя DNS-реестр и остальные карточки.

### DNS

Отдельно выполняются UDP и TCP к 127.0.0.1:5300, локальный DoH
к 127.0.0.1:3001/dns-query и публичный HTTPS DoH. Порты можно изменить.
Запрос A по умолчанию использует example.com. Проверяются ID, вопрос, структура DNS,
RCODE и адреса в ответе. Для NOERROR нужен адрес в Answer; SERVFAIL и пустой ответ
не считаются успехом. NXDOMAIN выбирайте для специально заданного отсутствующего имени.
Усечённый UDP-ответ отмечается отдельно, результат TCP показывается независимо.

Для публичного DoH проверяются доверие к TLS-сертификату, имя и срок действия,
HTTP 200, application/dns-message и DNS-содержимое. HTML 200 и перенаправления
не считаются DoH. Разделение HTTP- и DNS-ошибок описано в
[RFC 8484](https://www.rfc-editor.org/rfc/rfc8484.html#section-4.2.1).

Полный секретный URL читается **на VPS** из обычного файла `/root/dns-doh-url`
(путь настраивается). Ссылки, специальные файлы и файлы более 2 КиБ не принимаются.
URL не передаётся приложению, не сохраняется в его карточках/экспорте и не выводится
в ошибках. Пользователю SSH нужны права чтения; автоматического sudo нет.
Отсутствующий файл — «не настроено», недостаточные права — «недоступно для проверки».

### Chatmail

Укажите почтовый домен из сертификата — приложение его не угадывает.
SSH-проверки обращаются к loopback VPS, но TLS проверяет заданное доменное имя.
Проверяются SMTP STARTTLS (25, 587), SMTPS (465), IMAP STARTTLS (143), IMAPS (993).
Порты можно изменить или отключить значением 0. Авторизация, отправка писем и создание
аккаунтов не выполняются. Успешный результат подтверждает приветствие и TLS,
но не доставку сообщений. Проверка TLS учитывает имя и доверие к сертификату, как описано
в [RFC 8314](https://www.rfc-editor.org/rfc/rfc8314.html#section-4.4).

TURN/3478 проверяется отдельным STUN Binding-запросом с проверкой ID транзакции;
успех означает только ответ STUN, а не TURN allocation/relay. Это частичная проверка,
а не зелёный статус TURN. Назначение STUN описано в
[RFC 8489](https://www.rfc-editor.org/rfc/rfc8489.html#section-2).
Для iroh/3340 проверяется только TCP-доступность, без утверждения о работоспособности
обмена через relay. Эти результаты не ухудшают оценку основных почтовых проверок.

## Время, ограничения и безопасность

Каждый результат содержит причину, время, длительность и источник **VPS через SSH**.
Через пять минут результат явно устаревает. Изменение параметров очищает видимый
результат; повторный запуск не оставляет предыдущую зелёную отметку при ошибке.
Последняя оценка функциональных проверок доступна в статусе/мониторинге до перезапуска
приложения; это ограниченный кэш в памяти, а не постоянная история доступности.

Диагностика делит с Net Tools ограничение в четыре одновременных запуска и использует
авторизацию, PIN, токен страницы и ограничение частоты. На VPS нужен Python 3.9+.
Удалённый процесс ограничен 30 секундами; ответы ограничены по размеру.
Нет установки пакетов, изменений DNS/firewall/Caddy/почты/служб, перезапуска VPS или
автоматического исправления. Публичный DoH разрешает только публичные IP и закрепляет
соединение за проверенным IP; перенаправления и переменные HTTP-прокси не используются.

Проверка с VPS не доказывает доступность с домашнего ПК. Для публичного DNS и почты
используйте соответствующие Net Tools с компьютера приложения. Секретный DoH URL
с ПК этим интерфейсом не проверяется — поля для его ввода нет.
Работу NaiveProxy после изменений Caddy, доставку Chatmail и реальный TURN/iroh обмен
следует проверять отдельными клиентскими сценариями.

Автотесты без внешней сети: `tests/test_services/test_dns_mail.py`,
`tests/test_routes/test_dns_mail.py` и существующие тесты Net Tools/Projects.
