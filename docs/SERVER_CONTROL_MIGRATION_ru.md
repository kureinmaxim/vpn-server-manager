# Перенос управления TelegramOnly в VPN Server Manager

Статус: план согласован. Разработка версии **4.9.0** в ветке **codex/server-control**.
Исследованы локальные исходники VPN Server Manager `b397d1f` (4.8.0) и TelegramOnly `fcfa15a`.
Рабочие серверы не опрашивались и не изменялись.

### Реализовано в рабочей ветке

- Карточка сервера → Действия → Управление сервером; переход также доступен из мониторинга.
- Обзор использует существующие API «Статуса» (ОС, uptime, CPU, Docker) и мониторинга (службы, uptime и автозапуск). Каталог служб общий для всех трёх представлений. Из окна «Статус» можно перейти к управлению.
- Отдельная проверка точных целей systemd/Docker, включая остановленные контейнеры и Compose service labels. Несколько установок показаны отдельно.
- Запуск, остановка, перезапуск выбранной службы: одноразовый план на 5 минут, подтверждение hostname, привязка к SSH-хосту и сеансу, повторная проверка состояния.
- Проверенные SSH host keys, блокировка параллельных операций, проверка результата и приватный журнал `/var/log/vpn-server-manager-control.jsonl` без вывода команд и секретов.
- Интерфейс RU/EN/ZH. Новые зависимости и постоянно работающий агент не нужны.
- Просмотр имён клиентов из выбранного файла менеджера. Явная выдача URI для AnyTLS, TUIC, XHTTP и MTProto; прочие экспорты пока недоступны. Файл повторно проверяется по отпечатку перед выдачей, секреты не передаются в SSH argv и не возвращаются при загрузке списка. Поле со ссылкой очищается через минуту или при скрытии страницы. Это экспорт данных менеджера, без подтверждения их соответствия работающей службе.
- Чтение открытых параметров восьми протоколов из файлов менеджеров TelegramOnly: адрес, порт, SNI, режим и количество клиентов. Источники ищутся в стандартных каталогах, WorkingDirectory systemd-бота и bind mounts Docker-бота, включая остановленные контейнеры. Несколько источников и наличие 3x-ui отмечаются явно. Произвольный путь из браузера не принимается; файлы ограничены по размеру, ссылки не читаются, секреты исключаются белым списком полей.

Это просмотр файлов менеджеров, а не проверка фактически применённой конфигурации. Переопределённые через окружение пути, данные внутри слоя контейнера и Docker volumes пока не читаются; отсутствие найденного файла не означает отсутствие протокола. Связь с каталогом/контейнером бота ещё не доказывает исключительное владение файлом.

**Ещё не реализовано:** редактирование конфигураций протоколов, клиенты/экспорт, автономные установщики, настройки Mesh/HA/Web/TLS и согласование записей с ботом. Управление жизненным циклом служб не является полным переносом TelegramOnly. Эта версия пока находится в разработке и не объявлена готовым релизом.

## Цель и интерфейс

В карточке сервера: **Действия → Управление сервером**. Используются существующие SSH-реквизиты этой карточки. Приложение может управлять сервером без Telegram и без установленного процесса бота. При установленном TelegramOnly сохраняются его конфигурации и клиенты.

Разделы страницы:

- Обзор: ОС, права root/sudo, установленные компоненты, занятые порты, состояние бота и способ запуска каждого сервиса.
- Протоколы: конфигурация, установка/обновление, проверка, применение, запуск/остановка/перезапуск, журнал.
- Клиенты: создание/отзыв профилей, ссылки и экспорт поддерживаемых форматов. В автономном режиме идентификатор клиента не требует Telegram ID.
- Mesh и HA: Headscale, Headplane, Tailscale/exit node, Reticulum и связанные службы.
- Веб и TLS: Nginx, маршрутизация, сертификаты и обновление сертификатов.
- Обслуживание: обновления, резервные копии, дисковое пространство и существующая очистка стека.
- TelegramOnly: обнаруженная установка, состояние и управление ботом, если он установлен.

Русский, английский и китайский языки, существующие светлая/тёмная темы. Изменения показываются как план с конкретными сервисами и файлами; установка не запускается при открытии карточки.

## Что обнаружено

`admin_cli.py` и `scripts/bot_cli.sh` уже позволяют выполнять часть действий без Telegram. Однако CLI не покрывает все менеджеры протоколов. При существующем, но остановленном контейнере бота `bot_cli.sh` прекращает работу. Поэтому этот CLI полезен как совместимый дополнительный путь, но не может быть единственным исполнительным механизмом.

`host_utils.py` использует `nsenter` из контейнера. `compose.yaml` отдельно монтирует конфигурации менеджеров и системные конфиги. Следовательно, способ запуска бота не определяет способ запуска VPN-сервиса: бот в Docker может управлять Xray в systemd.

В VPN Server Manager уже существуют каталог служб в `ssh_service.py`, статус/мониторинг, SSH-реквизиты из карточки и сценарий plan/apply в `routes/reset.py`. Их следует расширять и переиспользовать, сохраняя текущие функции.

## Исполнение без зависимости от бота

1. VPN Server Manager соединяется с хостом через проверенный SSH host key.
2. Небольшой версионированный исполнитель передаётся через SSH. Ему не нужен постоянно работающий агент, Telegram-токен или открытый HTTP-порт.
3. Исполнитель выполняет только операции из каталога и возвращает структурированный JSON. Не принимает произвольные shell-команды из формы.
4. Для каждого компонента отдельно определяются `systemd`, Docker Compose, отдельный контейнер, отсутствие установки или неоднозначность.
5. Для Compose фиксируются project/service и источники конфигурации; для systemd — точный unit и фактические файлы. Не применяется глобальное `docker compose down`.
6. При нескольких установках пользователь выбирает целевую. Остановленный бот не запускается автоматически ради управления другим сервисом.

Для чистого сервера установщики должны быть адаптированы к отдельным протоколам: общий bootstrap TelegramOnly настраивает и бот, и обслуживание, поэтому его нельзя автоматически использовать как установщик любого выбранного сервиса.

## Совместная работа с ботом

На существующем сервере нужно согласовать два уровня данных: `*_config.json` менеджера и фактический конфиг сервиса. Только изменение `/etc/...` недостаточно: следующее применение из бота может его затереть.

- Обнаруживать bind mounts и владельца конфигурации, не предполагать фиксированный каталог установки.
- Перед записью сравнивать отпечатки конфигов с прочитанной версией. При изменении ботом — остановить применение и предложить обновить план.
- В автономном режиме использовать отдельное приватное хранилище метаданных на хосте.
- Если сервис управляется 3x-ui, использовать API владельца, не переписывать его Xray-конфиг напрямую.
- Для полной защиты от одновременных записей потребуется общий протокол блокировки, поддерживаемый и ботом. Без него нельзя обещать бесконфликтное одновременное применение из двух интерфейсов; до адаптации бота запись требует согласованного окна обслуживания.

## Запись и восстановление

<!-- WARNING: В исследованных AnyTLS/XHTTP apply_config используются прямой open(..., 'w') и немедленный restart без предварительной проверки/резервной копии. Такие записи нельзя переносить буквально: конфиги могут содержать секреты, а права зависят от umask. -->

Запись адаптируется: приватные права, резервная копия, проверка синтаксиса, сравнение версии, изменение только выбранного компонента, проверка состояния после перезапуска. Для файловых Docker bind mounts отдельно учитывать сохранение inode: обычный atomic rename может оставить контейнер со старым файлом. При частичном сбое показывать точный результат и доступное восстановление, не повторять действие вслепую.

Секреты передаются через защищённый SSH stdin/SFTP, не через argv; не попадают в журнал операций или диагностический JSON. Клиентские ссылки и QR выдаются отдельно как секретные данные. Полные `docker inspect`/`systemctl show` с переменными окружения не возвращаются в UI.

## Последовательность реализации

1. **Основа:** каталог возможностей, обнаружение хоста/компонентов, отдельная страница управления, SSH-исполнитель, plan/apply, журнал без секретов. Проверить отсутствие бота, systemd, Docker и смешанную установку.
2. **Протоколы:** перенос моделей и валидаторов каждого протокола, управление клиентами, применение и экспорт. Явно отмечать неподдерживаемые действия, пока они не перенесены.
3. **Mesh / веб / обслуживание:** Headscale, Tailscale, HA, Nginx/TLS, резервные копии и обслуживание.
4. **Установка и совместимость:** автономная установка, необязательный бот, согласование существующих конфигов и сценарий остановленного контейнера; полный прогон проверок, переводы и сборка.

Этапы — порядок реализации, а не замена полного переноса одной страницей статуса. Готовность каждого действия отмечается отдельно в карте возможностей.

## Критерии приёмки

- Проверки выполняются на тестовых сценариях без подключения к рабочим VPS.
- Действия адресованы конкретному SSH-хосту и компоненту, привязаны к PIN/CSRF и одноразовому плану.
- Креды не появляются в процессах/логах/ошибках; произвольные строки не становятся командами.
- Проверены смешанный режим, остановленный контейнер, недостаточные права, тайм-аут, изменённый конфиг, неверный сертификат/порт, занятый порт и частичный отказ после записи.
- Работают установка выбранного протокола без бота, чтение существующего конфига, изменение клиента и откат доступных изменений.
- После реализации — проверка на согласованном тестовом сервере. Изменение рабочих серверов не входит в текущий аудит и не выполняется автоматически.

При переносе кода сохраняется MIT-уведомление TelegramOnly и фиксируется исходная ревизия. Личные конфиги, `.env`, пользовательские данные, токены и приватные адреса не копируются.
