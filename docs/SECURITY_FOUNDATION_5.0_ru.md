# 5.0.0: первый блок защиты данных и доступа

Дата: 26.10.2026. Ветка: `codex/5.0-security-foundation`. Основа: 4.16.0, коммит `6b70c50`.

Это первый блок этапа A плана развития. Версия исходников поднята до 5.0.0 штатным инструментом: изменения намеренно несовместимы с частью прежнего поведения. Это **не публикация готовой macOS-сборки**. Установленное приложение и реальные серверы при разработке не изменялись.

## Что изменено

### Сохранность инвентаря

- Ошибка дешифрования, пустой/невалидный файл и отсутствие выбранного файла больше не означают пустой список серверов. Главная показывает ошибку с переходом в настройки, запись поверх повреждённого содержимого запрещена.
- Серверы и DNS сохраняются одним зашифрованным снимком. Невалидная структура DNS больше не заменяется молча пустым объектом.
- Запись: временный файл в той же директории, режим 0600 на POSIX, flush/fsync, атомарная замена. После замены синхронизируется директория на POSIX.
- До замены сохраняется предыдущий шифротекст в `<имя файла>.backup.enc`. Если сохранить резервную версию не удалось, основной файл не заменяется.
- Блокировка через стабильный соседний `.lock` сериализует писателей, в том числе разные процессы. Отпечаток прочитанного шифротекста позволяет отклонить устаревшую запись.
- Снимки серверов/DNS несут версию чтения. В HTTP-запросе версия также сохраняется отдельно, чтобы фильтрация списка при удалении или нормализация DNS не теряла контроль конфликта.
- Настройки профиля и PIN записываются атомарно с проверкой версии конфигурации. Повреждённый профиль нельзя перезаписать значениями по умолчанию. Чтение настроек UI может использовать безопасные значения для отображения, но такой результат нельзя сохранить поверх повреждённого файла.
- Имена импортированных файлов дополнены случайным идентификатором: два импорта за одну секунду не записывают в один путь.

Контроль версий защищает пересекающиеся операции чтения/записи. Он **не является версией HTML-формы**: две давно открытые формы, отправленные последовательно, пока не получают отдельную проверку устаревания. Это следующий шаг для редакторов карточек.

### Доверие SSH

Все новые SSH-подключения, включая мониторинг и его установку/удаление, загружают `known_hosts` и отклоняют неизвестный или изменившийся ключ сервера. Принятие неизвестного ключа без проверки отключено.

Для первого подключения:

1. Получите fingerprint сервера через независимый доверенный канал, например консоль провайдера.
2. Выполните OpenSSH-подключение к **тому адресу и порту, который используется карточкой**. Для тестового примера: `ssh -p 2222 operator@192.0.2.10`.
3. Сравните fingerprint. Сохраняйте ключ только при совпадении.
4. Повторите проверку из приложения.

Для нестандартного порта запись обычно имеет вид `[192.0.2.10]:2222`. LAN, mesh, IP и DNS-имя могут требовать отдельных записей. При неожиданной смене ключа сначала выясните причину; автоматического удаления старого доверия нет. `ssh-keyscan` без независимой проверки fingerprint не устанавливает доверие.

В 5.0.2 добавлены общие сообщения с endpoint и публичными fingerprint, а также перепроверка доверия при следующем SSH-доступе (см. ниже). Встроенный диалог принятия ключа не добавлен: доверие по-прежнему устанавливается через OpenSSH после независимой проверки.

### HTTP и PIN

- Все POST/PUT/PATCH/DELETE требуют CSRF-токен сессии. Явно чужой Origin отклоняется. Общий код добавляет токен в формы и same-origin fetch.
- Проверки auth/PIN продолжают выполняться на защищённых маршрутах; наличие CSRF само по себе не даёт прав.
- При отсутствии отдельной настройки `TRUSTED_HOSTS` принимаются только localhost/loopback host names. Произвольный Host отклоняется.
- Установка и удаление мониторинга используют POST-поток с событиями. Автоматического повторного подключения, повторяющего операцию, нет. При обрыве сначала проверьте состояние узла.
- GET `/shutdown` больше не завершает приложение; процесс закрывается через окно. HTTP-маршрут закрытия не отправляет сигналы процессу. Отдельный desktop exit требует auth/PIN и CSRF.
- PIN-проверки используют общий лимит процесса: 10 запросов за 60 секунд. Новая cookie не обнуляет лимит. Старое ограничение неудачных попыток сессии также сохранено.
- Старый вход через HTML-форму использует PIN профиля. Нечитаемая конфигурация не разрешает вход по стандартному PIN.
- Убраны тела auth-запросов, дампы сессий и фрагменты ключа из диагностического логирования. Журналирование HTTP использует путь без query string.

PIN остаётся блокировкой интерфейса, не паролем шифрования vault. Лимит сбрасывается при перезапуске процесса и не является распределённым лимитом для нескольких экземпляров веб-сервера. Эта итерация рассчитана на локальное приложение с одним процессом и потоками. Отдельный постоянный job API для установки пока не введён.

### Боты и команды терминала

- Рабочий probe больше не вызывает поиск токенов, getMe, сканирование командных строк и launchd plist, независимо от старой настройки getMe.
- Используются метаданные systemd/Docker, точные имена процессов и ограниченная health-проверка loopback. Для curl отключено использование прокси.
- Старые поля команд/задач сохраняются для совместимости, отображаются как readonly и не участвуют в проверке. Боты, заданные только ими, не будут обнаружены; используйте systemd/container/process selectors.
- Бот без процесса не получает выдуманный статус. Уведомляющие боты больше не ищутся по источникам токенов.
- Копируемые команды SSH формируются как аргументы с POSIX quoting. Путь `~/…` разворачивается на компьютере приложения. Подсказка допускает запрос пароля ключа или сервера.
- Команда на карточке по-прежнему указывает основной адрес; автоматический выбор mesh/LAN при SSH-проверке — отдельный механизм. Выравнивание выбора адреса и поддержка PowerShell остаются следующими задачами.

## Восстановление и совместимость

Формат основного Fernet-файла не изменён. Дополнительно появляются `.lock` и `.backup.enc`; последний содержит предыдущую зашифрованную версию. Храните ключ этой версии отдельно и не добавляйте пользовательские файлы в Git.

Если основной файл повреждён:

1. Закройте приложение и сохраните копию повреждённого файла для диагностики, не заменяя его.
2. Скопируйте `.backup.enc` под новым именем. Для открытия нужен ключ, которым зашифрована эта резервная версия.
3. В настройках импортируйте проверенную копию как новый файл и прикрепите её. Не запускайте запись поверх повреждённого оригинала.
4. Проверьте карточки и DNS перед дальнейшими изменениями.

При конфликте записи обновите страницу и повторите изменения. Последовательный откат и восстановление версии — действия пользователя; автоматического слияния несовместимых изменений нет. Старые версии приложения не соблюдают новые блокировки: не запускайте 4.x и 5.x одновременно с одним профилем.

Атомарная замена рассчитана на обычный локальный filesystem. Гарантии сетевых файловых систем/облачной синхронизации и поведение Windows после внезапного отключения питания отдельно не проверялись. Режим 0600 не заменяет ACL Windows.

## Проверки

Проверки используют временные каталоги, одноразовые ключи и вымышленные записи. Подключений к реальным VPS/NAS не было.

- Полный `venv/bin/python -m pytest -q`: **811 passed**, 20,58 с; покрытие **72,25%** при пороге 34% (macOS, Python 3.13.9).
- `node --test tests/js/http_security.test.cjs`: 3 проверки — same-origin CSRF, обычные/динамические формы, фрагментированный UTF-8 в POST SSE без reconnect.
- Реальный Paramiko handshake через `socketpair`: известный ключ разрешает вход; неизвестный и изменённый отклоняются **до передачи пароля**.
- Два процесса одновременно читают один vault: сохраняется один снимок, второй получает конфликт.
- Повреждённый vault, неправильный ключ, невалидный DNS, удалённый активный файл, сбой backup/final replace, восстановление копии в новый файл.
- Raw Flask clients: CSRF без токена/с неверным и Unicode-токеном, Origin/Host, лимит с новыми cookie, legacy login, запрет GET-операций, отсутствие PIN-canary в журнале.
- `tools/check_public_files.py`: проверка приватных путей; это не полный secret scan.
- Версионные файлы согласованы штатным `tools/update_version.py status`.

## Что ещё не закрыто

Следующие пункты нельзя считать завершёнными только по зелёным тестам этой ветки:

1. Мастер восстановления профиля из UI. Восстановление прерванной смены ключа реализовано в 5.0.1 (см. ниже); сценарий с повреждением самого журнала требует ручного восстановления из сохранённых снимков.
2. Встроенный интерфейс подтверждения host key остаётся отдельной задачей. Понятные причины отказа и отзыв открытых сессий реализованы в 5.0.2 с ограничениями, описанными ниже.
3. Конфликты давно открытых форм, точный выбранный endpoint в копируемой команде, ошибки записи UI preferences и других legacy-экранов.
4. Cookies/CSP/CDN и проверка WebView на чистых macOS/Windows. Новая CSRF-обвязка проверена тестами, но это не полноценный native UI smoke test.
5. Модель защищённого backup/export: старые экспортные функции могут складывать ключ и данные вместе. Новая зашифрованная резервная версия vault не меняет этот сценарий.
6. Этап B: окончательная подпись macOS, архитектуры, чистая установка/upgrade/restore, только затем release asset. Собранный пользователем пакет 4.16.0 этой работой не пересобирался.
7. Затем этапы C/D: onboarding, вычитка интерфейса, профессиональные SSH-сценарии и измерение масштаба.

Подробный исходный аудит остаётся локальным документом и не включается в публичный коммит этой ветки. Этот файл описывает изменение поведения и границы текущей реализации.

## Продолжение: 5.0.1 — восстановление при смене ключа

Дата: 27.10.2026. Полный pytest: **831 passed**, покрытие **72,61%**; 20 новых проверок смены ключа. CI первого блока 5.0.0 также прошёл на Linux/Python 3.11.

Смена ключа вынесена в отдельный сервис. Порядок: блокировка профиля → проверка текущего ключа/выбранного файла → полная перешифровка в новый уникальный `.enc` → проверка нового файла → сохранение временных снимков `.env`, `config.json` и поколения профиля → переключение файлов → запись признака завершённой транзакции. Только после этого обновляются сервис данных и конфигурация работающего приложения.

При обычной ошибке ввода-вывода до завершения выполняется откат. При прерывании процесса незавершённая транзакция восстанавливается на следующем запуске **до загрузки ключа и регистрации сервисов**. Если признак завершения уже сохранён, используется новая версия профиля. Восстановление можно безопасно повторить, если оно само было прервано. Неопределённый результат синхронизации commit-маркера оставляет журнал на месте и блокирует дальнейшие записи до восстановления.

Старый vault не перезаписывается. Отдельный идентификатор поколения запрещает запись и чтение через устаревший экземпляр менеджера; другой процесс приложения после смены ключа должен перезапуститься. Общая блокировка профиля также охватывает запись обычного vault и конфигурации. Это защищает экземпляры 5.0.1+, но не делает безопасным одновременный запуск старой 4.x/5.0.0 версии.

Журнал `.key-rotation.pending` не содержит ключей. Временный каталог `.key-rotation-*` содержит **конфиденциальные исходные файлы**, включая ключ: каталог создаётся с режимом 0700, файлы — 0600 на POSIX. После успешного завершения/отката снимки удаляются; сбой до создания маркера или при очистке может оставить закрытый каталог. Не прикладывайте его к issue/support bundle, не копируйте в пакет приложения. Gitignore и privacy checker исключают эти пути. ACL Windows и защищённое удаление с SSD этой гарантией не покрываются.

Проверяются пропавший активный файл, неверный ключ профиля, повреждённый внутренний пароль, сохранение DNS/SSH/настроек, конфликт устаревшего config и запуск с устаревшим ключом в конфигурационном классе. Все пять точек переключения протестированы с искусственным прерыванием. Отдельный процесс завершается через `os._exit` посреди переключения; последующее восстановление возвращает читаемый прежний профиль.

Это исправление не добавляет backup ключа для произвольного отката **после успешной смены**: храните старый ключ отдельно, если хотите впоследствии открыть старые `.enc`. Исходный формат зашифрованного инвентаря не изменён.


## Продолжение: 5.0.2 — доверие SSH и отзыв подключений

Неизвестный ключ, несовпадение ключа и нечитаемый `known_hosts` теперь имеют отдельные сообщения. Для неизвестного ключа показаны адрес с портом и полученный публичный SHA256-отпечаток; для изменившегося — также ожидаемый отпечаток. Пароли, приватные ключи и исходный текст исключения в этих сообщениях не выводятся. Приложение не предлагает безусловно удалить старую запись и не принимает ключ автоматически.

Некорректные записи и неподдерживаемые маркеры OpenSSH (`@cert-authority`, `@revoked`) блокируют загрузку доверия целиком: строки больше не пропускаются молча. Поддержка сертификатов OpenSSH этим изменением не добавлена.

После успешного сохранения нового пароля, ключа, парольной фразы, пользователя, порта или адресов карточки закрываются существующие подключения к затронутым адресам в текущем процессе. Это включает выделенные подключения операций; при совпадении адресов могут закрыться подключения другой карточки. Изменение названия и повторное шифрование того же пароля не вызывают отключения. Ошибка записи не отзывает сессии. Подключение, начавшееся до отзыва, не сможет вернуться в пул после завершения handshake.

Пул сверяет HMAC-подпись параметров авторизации, содержимого файла ключа и доверия. Случайный ключ HMAC живёт только в памяти процесса; исходные секреты не сохраняются в подписи и не журналируются. Замена файла приватного ключа по прежнему пути обнаруживается при следующем получении соединения из пула. Изменение, удаление или недоступность `known_hosts` отзывает подключения при следующем SSH-доступе. Фонового наблюдателя файлов нет; отдельно работающие процессы не получают мгновенное уведомление об отзыве.

Закрытие транспорта не гарантирует остановку уже запущенной команды на сервере. Автоматического повтора операций нет. Установленное macOS-приложение не обновлялось; сборка и ручная проверка нативного интерфейса остаются отдельным этапом.

Регрессионные тесты используют временные ключи, mock-транспорты и локальные проверки Paramiko: повторное использование, смена параметров и файлов, гонка при handshake, отказ записи, публичные отпечатки и отсутствие секретов в сообщениях. Реальные VPS/NAS не опрашивались.

Проверка 5.0.2: полный pytest — 851 тест, покрытие 73,13%; Node — 3 теста; проверка публичных файлов и синхронизация версий пройдены. Тесты изолированы от пользовательского домашнего каталога и его SSH-файлов.

## Продолжение: 5.0.3 — локальная macOS-сборка (этап B)

Скрипт больше не копирует конфигурацию проекта в рабочий профиль установленного приложения. Версия берётся из отслеживаемого шаблона. Результаты и кэш помещаются в отдельные `dist/macos-local` и `build/macos-local`; предыдущие артефакты вне этих каталогов сохраняются.

Удалён ручной fallback-конструктор некорректного `.app`. Используется bundle PyInstaller: итоговый plist объединяется с шаблоном с сохранением имени исполняемого файла и иконки. Архитектуры всех Mach-O зависимостей проверяются на совместимость. Минимальная версия macOS выводится из `LC_BUILD_VERSION`/`LC_VERSION_MIN_MACOSX`, а не из SDK или версии исходников библиотеки. Это техническая нижняя граница, а не обещание поддержки без проверки на соответствующей ОС.

После всех изменений применяется ad-hoc подпись внешнего bundle и обязательная `codesign --verify --deep --strict`. Вложенный код уже подписан PyInstaller. Копирование в DMG сохраняет символьные ссылки; копия приложения также проверяется, затем проверяется контрольная сумма образа через `hdiutil verify`. Ошибка любого обязательного этапа завершает сборку неуспешно. Рядом с образом создаётся JSON с архитектурой, версией, минимальной macOS, статусом подписи и SHA-256.

Это исправление локальной цепочки сборки, **не завершение всего этапа B**. Developer ID, hardened runtime, нотарификация/stapling, Gatekeeper и чистая установка/upgrade/restore ещё требуют отдельной работы. Установленное приложение не заменялось, профиль не изменялся, артефакты не опубликованы. Инструкция не предлагает отключать Gatekeeper.

Основание порядка подписи: [Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/) и [PyInstaller macOS feature notes](https://pyinstaller.org/en/stable/feature-notes.html). Проверки включают настоящий codesign на тестовом Mach-O, обнаружение изменения plist после подписи, несовпадение архитектур, ошибки подписи и манифест без локальных путей.

Результат проверки 27.10.2026: 858 Python-тестов и 3 JS-теста прошли; покрытие приложения 73,13%. Полный локальный PyInstaller bundle (96 Mach-O файлов) прошёл строгую проверку подписи, DMG — `hdiutil verify`. Полученная архитектура — arm64; минимальный бинарный target — **macOS 26.0**, заданный Python/OpenSSL и модулями текущего Homebrew-окружения. Для более старых macOS необходимы совместимые сборочные зависимости, а не занижение значения plist. Проверка упаковки не подтверждает первый GUI-запуск или восстановление профиля на чистом Mac.

## Продолжение: 5.0.4 — независимость от Homebrew macOS 26

Добавлен `python3 tools/build_macos_compatible.py`: uv устанавливает CPython 3.13.12 в каталог проекта, создаёт отдельное окружение и синхронизирует hash-locked зависимости из `requirements/macos-arm64.lock`. Основное окружение разработчика и системный Python не меняются. Native-зависимости устанавливаются из wheels; исключение — чистый Python `proxy-tools`, исходный архив которого также зафиксирован по хешу. Сборочные инструменты изоляции source-пакета не полностью зафиксированы: побитовая воспроизводимость не заявляется.

Цель этой сборки — Apple Silicon/macOS 13. Все Mach-O файлы проверяются: требование более новой ОС завершает сборку ошибкой до подписи. Простая замена `LSMinimumSystemVersion` не считается исправлением. Порог в plist не ниже выбранной цели, а `binary_minimum_macos` отдельно показывает измеренную нижнюю границу бинарей.

Перед созданием DMG запускается готовый executable с `--build-smoke-test`: загрузка SSL, UI, SSH, изображений и криптографии плюс синтетический Fernet round-trip. Этот режим не создаёт профиль, не открывает окно и не подключается к серверам. Проверка на машине сборки не заменяет GUI/upgrade/restore испытания на macOS 13.

Intel не объявлен поддержанным этой цепочкой: cryptography 50 не публикует macOS x86_64 wheels. Автоматический откат криптографической библиотеки исключён; нужен отдельный план поддержки Intel. Источники: [uv managed Python](https://docs.astral.sh/uv/concepts/python-versions/), [cryptography changelog](https://cryptography.io/en/stable/changelog/). Требования к Developer ID, нотарификации и чистому Mac остаются открытыми.

Фактический результат: ARM bundle 5.0.4 содержит 37 Mach-O файлов, максимальный бинарный target — 11.0, целевой минимум plist — 13.0. Packaged runtime self-check, строгая подпись и DMG checksum прошли. Полный pytest в обычном и новом изолированном окружениях: 860 passed (покрытие 73,13% / 73,14%); дополнительно проверен отказ Intel до скачивания зависимостей, 10 build-тестов прошли. Ни запуск GUI на macOS 13, ни совместимость Intel этим результатом не подтверждены.

## Продолжение: 5.0.6 — macOS-проверки в CI

В этап B добавлен настоящий macOS ARM build job на `macos-14`: изолированный Python, hash-locked зависимости, сборка `.app`/DMG и проверка публичных файлов. Отдельный verifier сверяет версию с исходниками, архитектуру, target 13.0 и SHA-256 образа, переносит `.app` во временный каталог и проверяет подпись и запуск dependency self-check с новым HOME. Создание рабочего профиля в этом режиме считается ошибкой.

CI сохраняет только JSON-манифест и отчёт на 14 дней; бинарники не публикуются как release asset. Отчёт явно содержит OS машины проверки, `gui_tested: false` и `notarized: false`. Проверка перемещённого `.app` не является установкой из DMG, GUI-smoke, upgrade/restore или подтверждением работы на macOS 13. Эти части этапа B, Developer ID и Windows packaging CI остаются открытыми.

Локально: 876 Python-тестов, 3 JS-теста, сборка и запуск перемещённого bundle прошли. Удалена параллельная настройка глобального fullscreen-меню macOS; остальные пункты масштаба сохранены.
