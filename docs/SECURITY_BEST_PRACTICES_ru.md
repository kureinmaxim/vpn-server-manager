# Рекомендации по безопасности для панели управления VPS

Этот документ описывает текущую модель безопасности приложения и даёт рекомендации по её улучшению в будущем.

## 1. Текущая модель безопасности

Приложение использует многоуровневый подход к защите данных, где разные типы информации защищаются по-разному в зависимости от их чувствительности.

### Хранение данных

*   **Конфиденциальные данные:** серверы и DNS-карточка лежат в одном зашифрованном файле `data/servers.json.enc`.
*   **Ключ шифрования:** главный ключ (`SECRET_KEY`) находится в `.env` — в корне проекта при разработке и в каталоге данных приложения (`VPNServerManager-Clean`) у собранной версии.
*   **PIN:** хранится отдельно, в `config.json`, и к шифрованию отношения не имеет.

**КРИТИЧЕСКИ ВАЖНО:** Файл `.env` **никогда** не должен попадать в систему контроля версий (Git) или публиковаться. Он содержит ключ ко всем вашим зашифрованным данным.

### Два слоя шифрования

1.  **Поля.** Каждый пароль и логин шифруется Fernet'ом по отдельности и хранится как токен `gAAAAA...`.
2.  **Файл.** Получившийся JSON шифруется Fernet'ом целиком.

Открытые пароли существуют только в оперативной памяти — в полях `*_decrypted`, которые создаются при загрузке и снимаются `_strip_runtime_secrets()` перед записью. На диск они не попадают. Подробности — в [SECRET_KEY_ru.md](SECRET_KEY_ru.md).

### Уровни безопасности по типам данных

| Тип данных | Метод защиты | Формат хранения | Уровень безопасности | Пояснение |
| :--- | :--- | :--- | :--- | :--- |
| **Пароли** (SSH, root, Панель, Хостер) | **Симметричное шифрование** (Fernet) | Зашифрованный | **Высокий** | Пароли никогда не хранятся в открытом виде. Они шифруются с помощью `SECRET_KEY` перед сохранением в JSON. |
| **Логины** (Панель, Хостер) | **Симметричное шифрование** (Fernet) | Зашифрованный | **Высокий** | Логины также шифруются для комплексной защиты учётных данных. |
| **Весь файл данных** | **Симметричное шифрование** (Fernet) | Зашифрованный | **Высокий** | Поверх полевого шифрования закрыт и сам файл, поэтому IP, заметки и DNS не видны без ключа. |
| **SSH-пользователь и порт** | **Отсутствует** | Открытый текст внутри файла | **Низкий** | Видны любому, кто расшифровал файл. |
| **URL-адреса** (Панель, Хостер) | **Маскировка (сокрытие)** | Открытый текст внутри файла | **Низкий** | URL хранятся в открытом виде, но на главной странице их пути скрываются для защиты от случайного взгляда. |
| **Прочие данные** (IP, заметки и т.д.) | **Отсутствует** | Открытый текст внутри файла | **Низкий** | Общая информация о серверах хранится как есть, в открытом виде. |
| **PIN** | **Отсутствует** | Открытый текст в `config.json` | **Низкий** | Не хешируется. Защищает только от случайного взгляда на незаблокированном компьютере, но не от того, кто читает файлы. |

### Что даёт PIN, а что нет

PIN блокирует интерфейс и хранится как есть в `config.json` → `secret_pin.current_pin`. Он **не участвует в шифровании**: данные защищены только `SECRET_KEY`.

*   Знание PIN без `.env` не даёт прочитать данные.
*   Доступ к `.env` и файлу `.enc` даёт прочитать всё, PIN при этом не помеха.
*   Подбор ограничен: 3 неверные попытки → блокировка на 30 секунд. Счётчик живёт в сессии, поэтому ограничение бьёт по сессии, а не по всем попыткам сразу.

Вывод: PIN — это замок на интерфейсе для общего компьютера, а не второй фактор защиты данных.

## 2. Будущие улучшения и лучшие практики

Текущая модель хорошо подходит для личного использования, но для повышения безопасности и масштабируемости проекта можно применить несколько лучших практик.

### Рекомендация №1: Переход от JSON к базе данных (например, SQLite)

Это самое значительное улучшение, которое можно сделать.

*   **Почему это важно?**
    *   **Масштабируемость:** Базы данных (БД) гораздо лучше справляются с большими объёмами данных и одновременными запросами.
    *   **Надёжность:** БД следят за целостностью данных и их типами.
    *   **Безопасность:** В БД встроены мощные механизмы безопасности, которые упрощают управление доступом и предотвращают ошибки при одновременной записи.
    *   **Производительность:** БД оптимизированы для быстрого поиска и обновления информации.
*   **Как применить:**
    1.  Выберите простую БД, например **SQLite**, которая хранит все данные в одном файле и не требует отдельного сервера.
    2.  Используйте библиотеку **SQLAlchemy**. Она позволяет работать с данными как с Python-объектами, что делает код чище и безопаснее.
    3.  Напишите небольшой скрипт для миграции: он один раз прочитает данные из `data/servers.json.enc` и перенесёт их в новую базу данных. Учтите оба слоя шифрования — поля останутся токенами `gAAAAA...` после расшифровки файла.

### Рекомендация №2: Чётко разделять секреты, runtime-конфиг и release-метаданные

Для текущего проекта не нужно переносить всю конфигурацию в `.env`.

*   **Почему это важно?** Разные типы конфигурации должны жить в разных местах:
    *   секреты и чувствительные переменные — в `.env`;
    *   локальные runtime-настройки пользователя — в `config.json`;
    *   release-версия репозитория — в `config/config.json.template`.
*   **Как применить:**
    1.  Оставляйте `SECRET_KEY` и другие чувствительные значения в `.env`.
    2.  Не используйте локальный `config.json` как источник версии релиза.
    3.  Для релизной версии и синхронизации файлов используйте `tools/update_version.py`.

### Рекомендация №3: Внедрить журнал аудита (логирование)

Отслеживайте важные события в приложении.

*   **Почему это важно?** Журнал аудита помогает понять, кто, что и когда сделал. Это бесценно для анализа безопасности и отладки.
*   **Как применить:**
    1.  Создайте новый механизм логирования (например, в файл `logs/audit.log` или в отдельную таблицу БД).
    2.  Записывайте такие события, как: "Пользователь X добавил сервер Y", "Пользователь X просмотрел пароль от сервера Z" и т.д.

### Рекомендация №4: Подготовка к реальному использованию (Production) с HTTPS

Никогда не используйте встроенный сервер Flask для реальной работы.

*   **Почему это важно?** Он небезопасен и не рассчитан на нагрузки. Весь трафик, включая пароли, которые вы просматриваете, передаётся в незашифрованном виде (HTTP).
*   **Как применить:**
    1.  Используйте профессиональный WSGI-сервер, например **Gunicorn**.
    2.  Настройте его для работы через обратный прокси-сервер **Nginx**.
    3.  С помощью **Let's Encrypt** получите бесплатный SSL/TLS-сертификат для Nginx, чтобы включить **HTTPS**. Это зашифрует весь трафик между браузером и вашим сервером.

### Рекомендация №5: Хранить PIN в виде хеша, а не открытым текстом

Сейчас PIN лежит в `config.json` как есть. Для локального приложения это осознанный компромисс, но у него есть цена.

*   **Почему это важно?** Любой процесс или человек с доступом к файлам читает PIN мгновенно. Он же попадает в резервные копии каталога данных и в скриншоты конфигурации.
*   **Как применить:**
    1.  Хранить не `current_pin`, а хеш с солью — например, `scrypt` или `argon2` из `cryptography` / `argon2-cffi`.
    2.  Сверять введённый PIN с хешем, а само значение нигде не сохранять.
    3.  Предусмотреть миграцию: при первом запуске после обновления заменить открытый `current_pin` на хеш.
    4.  Учесть, что экспорт `PIN.txt` в резервной копии после этого станет невозможен — его нужно либо убрать, либо оставить как добровольную напоминалку.
